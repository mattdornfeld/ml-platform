# Project conventions

- Use `/Users/matthewdornfeld/.virtualenvs/pytorch-tutorial/bin/python` as this repository's Python interpreter.
- Use absolute imports for all Python modules in this repository.
- Do not preserve obsolete schemas or paths with compatibility shims, symlinks, or fallbacks. Migrate data and update code to the current schema instead.
- When the user gives a goal, attempt straightforward fixes for errors encountered while pursuing it without stopping to ask for permission. Ask only when progress depends on a consequential decision or unavailable information.
- Put values derived from materializer instance configuration behind descriptive private instance properties rather than recomputing them inside workflow methods.
- Call materializer instance behavior through `self`, including transform instantiation, rather than naming the concrete class.
- Break complex nested transform and DataFrame expressions into named steps or multiline keyword arguments.
- Use descriptive variable names that explain the data or role of each intermediate value.
- Prefer frozen dataclasses for materializer instance properties. Avoid mutable materializer instance state; pass or recompute transient workflow data instead of assigning mutable caches to `self`.
- Do not infer or derive runtime behavior, schemas, partitioning, or other implementation details from metadata without explicit user approval. Prefer static declarations and strong types.
- Do not introduce optional properties, arguments, or return types without explicit user approval. Prefer required, statically typed interfaces.
- For exhaustive structural pattern matching, use `case _ as unsupported_value:` followed by `assert_never(unsupported_value)` rather than a bare capture pattern or `case _:`. This preserves a clear wildcard branch and enables static exhaustiveness checking.
- Keep classes public unless they are intentionally module-internal implementation details. Minimize each class's public method surface by making implementation methods private; retain public methods only for explicit contracts and entry points.
- Do not use `getattr`, `setattr`, `hasattr`, `delattr`, or `object.__setattr__` without explicit user approval. Prefer declared, statically typed interfaces and immutable constructor values.
- Encapsulate partition-cadence data on `PartitionType`; do not repeat conditional mappings such as hourly-to-hour in materializers.
- Store normalized requested partition timestamps behind a descriptive property on the relevant materializer configuration rather than constructing them in workflow or validation methods.
- Keep `validation_configs` declarative: it must return only that materializer's simple declared configuration list. Apply YAML validation overrides once in the base materializer to preserve DRY configuration resolution.
- Prefer enums over string literals for domain concepts in configuration and validation models; pass the enum itself through contracts rather than a derived string value.
- Use descriptive variable names. Prefer `data_frame: DataFrame` over generic `frame: DataFrame`.
- In dataclass-style classes, declare instance properties at the top of the class body. Put methods that define static or class-level values below those properties.
- Prefer Pydantic `model_validator(mode="after")` for validation of complete data models; use field validators only when validation is inherently local to one field.
- Do not create methods that only return their input or otherwise perform no work. Remove them and call the meaningful operation directly.
- Do not create a property for data used only once, or when inlining is equally clear; inline it at the call site.
- Encapsulate construction of an object's derived representation inside that object. Pass typed source values to its constructor rather than assembling internal SQL, properties, or similar representations at call sites.
- Do not use `typing.cast` without explicit user approval. Prefer generics, protocols, type guards, or stronger interfaces that preserve the concrete type.
- Prefer specialized field types in child classes over union field types in parent classes. Use a generic parent contract when shared behavior needs to retain the child's concrete type.

- Explicitly model external-data and transformation outputs with named, strongly typed classes rather than anonymous broad containers such as `tuple[object, ...]`.
- Ask the user before changing a public API contract, including endpoint shapes, API DTOs, or user-facing configuration schemas.
- Ask before introducing broad container types such as `dict[str, object]` or `dict[str, Any]`. They are exceptional escape hatches, not defaults; prefer explicitly modeled, strongly typed data structures.
